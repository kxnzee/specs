**Jira Story:** JIT-002

## Why

В `jitsi-web` уже реализован request/approve-flow для Visitor: зритель может
"поднять руку" (`promotion-request`), после чего модератор видит запрос в
списке ожидающих (`VisitorsList`/`VisitorsItem`) и может его одобрить или
отклонить (`approveRequest`/`denyRequest`/`admitMultiple`). Отдельно уже
существует полный, с поиском, список всех текущих зрителей
(`CurrentVisitorsList`, за JWT-фичей `LIST_VISITORS`) — но у элементов этого
списка нет действия "включить в разговор": он read-only. Также уже полностью
реализован обратный перевод участника в зрители (`DemoteToVisitorButton`/
`DemoteToVisitorDialog`, `demoteRequest`).

Реальный пробел: модератор не может проактивно выбрать конкретного зрителя из
уже существующего полного списка и включить его в разговор без того, чтобы
зритель сначала сам запросил слово (raise hand). Это блокирует сценарии, где
инициатива должна исходить от модератора — например, интервью со зрителем или
адресный вопрос в большой трансляции, когда сам зритель мог не поднимать руку.

## What Changes

### Новое в рамках JIT-002
- Действие "включить в разговор" на произвольном элементе уже существующего
  списка зрителей (`CurrentVisitorsList` или эквивалентного представления),
  инициируемое модератором без предварительного запроса от зрителя.
- Клиентская обработка на стороне промотируемого зрителя: перевод из
  receive-only в состояние с правом отправки аудио. Существующий код содержит
  такой cycle только для обратного направления (demote:
  `disconnect(true)` → `setPreferVisitor(true)` → `connect()`); симметричный
  путь для promote в `jitsi-web` не найден и требует реализации или
  подтверждения, что это уже покрыто внешней зависимостью (`lib-jitsi-meet`,
  не входит в зарегистрированные Code Repositories) — открытый вопрос для
  Design.
- Право на отправку аудио выдаётся сразу замьюченным — зритель включает
  микрофон сам (явно согласовано в Explore).
- Микрофон стартует замьюченным; видео при promote не включается (audio-only,
  явно согласовано в Explore).
- Действие доступно той же роли moderator, что уже управляет mute/kick и
  demote — новая роль или право не вводятся (явно согласовано в Explore).

### Переиспользуется без изменений
- Возврат зрителя обратно в Visitor — существующий `demoteRequest(id)`
  принимает произвольный `id` участника и не ограничен теми, кто пришёл через
  request; отдельный "revert"-механизм для promoted-by-moderator зрителей не
  нужен (явно согласовано в Explore: ручной revert модератором, без
  auto-revert по таймеру).
- Существующий request/approve-flow (raise hand → promotion-request →
  approve/deny) не изменяется и не используется как предпосылка для нового
  действия — оба пути включения сосуществуют независимо.

### Явно вне MVP
- Массовое включение нескольких свободно выбранных (не запросивших слово)
  зрителей одним действием — `admitMultiple` сегодня работает только по
  списку pending-запросов, на новый путь не распространяется.
- Изменения в `jitsi-videobridge` не предполагаются на этапе Proposal — в
  репозитории не найдено кода, специфичного для visitor promote/demote;
  подтверждение или опровержение потребности в изменениях там — задача
  Design, а не текущего документа.

### Открытые вопросы для Design
- Достаточно ли существующего канала сообщений между главной комнатой и
  зрителем (тот же, что используют `promotion-request`/`demote-request`) для
  адресного сообщения от модератора зрителю, который ничего не запрашивал —
  или для этого нужен путь через `VisitorsManager`/`VisitorsIq` в
  `jitsi-control`, чей текущий диспетчер помечен `// TODO pass to the
  conference` и не дописан. Подтверждено, что обработка перехода роли
  `MemberRole.VISITOR` ↔ не-`VISITOR` через MUC presence в
  `ChatRoomMemberImpl` (`jitsi-control`) сегодня явно **блокируется** для
  не-первого presence: изменение роли игнорируется с предупреждением
  `"Member role changed ... - not supported!"`, а сама роль не обновляется
  (`ChatRoomMemberImpl.kt:196-204`). Это не кандидат на reuse без изменений —
  presence-путь для нового действия не подходит как есть, что усиливает
  необходимость доработки именно `VisitorsManager`.
- Является ли текущий clientside-переход в promote полностью in-place, или
  так же, как demote, требует внутреннего reconnect на уровне соединения
  (`disconnect`/`connect`). Продуктовое требование — только отсутствие
  видимого для пользователя повторного входа (потери state, экрана
  "you left"); допустимое внутреннее переподключение самим механизмом не
  запрещено и уже является принятым паттерном для demote.

## Capabilities

### New Capabilities
- `conference/visitor-promotion`: возможность модератора включить в разговор
  конкретного зрителя из полного списка зрителей конференции, без
  предварительного запроса от самого зрителя, с правом отправки аудио
  (стартующим замьюченным) и без видимого для пользователя выхода из
  текущей встречи.

### Modified Capabilities
- (нет) — в `openspec/specs/` нет ни одной существующей capability spec;
  уже реализованный request/approve-flow и demote ранее не были
  формализованы как OpenSpec capability и не входят в этот Change как
  Modified (их наблюдаемое поведение не меняется).

### Repository impact

| `jitsi-control` | implementation | Доработать маршрутизацию адресного сообщения от модератора к зрителю, не отправлявшему request; вероятная точка входа — незавершённый диспетчер `VisitorsManager.processStanza` (`// TODO pass to the conference`). | Единственный найденный в этом репозитории признак незаконченной инфраструктуры именно для visitor-канала; существующая обработка `MemberRole.VISITOR` через MUC presence подтверждённо не подходит как есть — переход роли для не-первого presence явно блокируется (`ChatRoomMemberImpl.kt:196-204`, лог `"not supported"`), точный способ доработки уточняется в Design. |
| `jitsi-videobridge` | no-change | Изменений не предполагается. | В репозитории не найдено кода, специфичного для visitor promote/demote (совпадения по "promot"/"demot" относятся к `RecentSpeakersList` и не связаны с темой). Роль JVB endpoint для промотированного участника не должна предполагаться заранее — это подтверждается или опровергается в Design, не в Proposal. |

### Прочее затронутое

- Существующий request/approve-flow и demote-flow не меняются по поведению;
  затрагивается только добавление нового, независимого от них входа в то же
  конечное состояние (send-capable participant, стартующий замьюченным).
- Модель прав модератора переиспользуется без изменений.
